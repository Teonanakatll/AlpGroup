    # SPEC: складской учёт инструмента и снаряжения (AlpGroup)

Статусы пунктов: `[ ]` не начато, `[~]` в работе, `[x]` сделано, `[?]` не решено.
Принятые решения и их причины: `docs/DECISIONS.md`.

## 1. Цель

Учёт инструмента и снаряжения: что на балансе, что на складе, что и на какой объект выдано, кто взял и что вернули. Стек: Django + DRF, затем адаптивный сайт; Telegram-бот только для оповещений (позже).

Вне рамок на этом этапе: каталог проектов (фото, видео, данные заказчика, описание работ), сотрудники и бригады как отдельные сущности.

## 2. Два вида учёта

Правило: **дорогое и значимое учитывается поштучно, дешёвое и массовое количеством.** Решение принимается при постановке на баланс. Дорогой «ручной» инструмент заводится как штучный (`Tool`).

### 2.1 Штучный инструмент (`Tool`)
У позиции есть собственный статус и история.
- [ ] название, категория, примечание
- [ ] статус: на складе / выдан  / списан / в ремонте / не найден (хранится как кэш, меняется только сервисом)
- [ ] текущий объект (`current_site`, пусто, пока на складе; кэш, меняется только сервисом)
- [ ] дата постановки на баланс, дата снятия с баланса
- [ ] фото: несколько, одно главное (модель `ToolPhoto`)

### 2.2 Ручной инструмент количеством (`HandTool`)
- [ ] название, примечание
- [ ] `total` (всего на балансе), `issued` (на руках); `available = total - issued` вычисляется
- [ ] ограничение в БД: `issued <= total`
- [ ] `total` и `issued` меняет только сервис

### 2.3 Категории
- [ ] `Category` с необязательным родителем (подкатегории через админку по мере надобности)
- Верхний уровень: Электроинструмент, Снаряжение, Мелкий ручной.

### 2.4 Объект и вид работ (минимальный справочник)
- [ ] `Site`: название или адрес, вид работ
- [ ] `WorkType`: мойка, гидра, монтаж и т.д.

**План развития модели `Site` (07.11.2026, по запросу владельца; делаем постепенно, поля заводим заранее):**
- [ ] даты начала и окончания работ (план/факт); статус объекта (активен / приостановлен / закрыт)
- [ ] простой журнал по дням: короткие заметки по датам (что делали, кто был, расходы) — отдельная модель `SiteLogEntry(site, date, note, created_by)`, только дописывается, как остальные журналы
- [ ] отметка рабочего дня: полный день / полдня / выходной — для графического календаря по объекту (помесячная сетка, удобный дизайн)
- [ ] вложения: фото объекта и чеки (модель по образцу `ToolPhoto`: файл, подпись, кто загрузил); чеки отдельным типом вложения, чтобы потом свести расходы
- [ ] ответственный за объект (прораб/бригадир) — связь с ролями (см. раздел 7)
- [ ] что ещё понадобится — покажет практика

## 3. Журналы (только дописываются)

Два плоских журнала с общим абстрактным родителем `BaseMovement`. Одна строка равна одному событию по одной позиции.

Общие поля: тип операции, объект (`site`), «кто взял» (текст `taken_by`), время, кто внёс, `is_cancelled`, `note`, `batch` (необязательный UUID набора).

Типы операций:
- поставлен на баланс (`added`)
- выдан (`issued`)
- принят (`returned`)
- не найден (`missing`)
- в ремонте (`servicing`)
- списан (`written_off`)

- [ ] `ToolMovement` (+ `tool`)
- [ ] `HandToolMovement` (+ `hand_tool`, `quantity` не меньше 1)

Журнал источник истины. Статусы и счётчики в моделях инструментов это кэш для быстрых списков. Отмена: запись помечается `is_cancelled`, состояние инструмента пересчитывается из журнала.

### 7.1 Роли (решено 07.11.2026)
На небольшом складе инструмента ролей немного. В учётных системах (1С, WMS) это связка
«администратор — кладовщик (оператор) — наблюдатель», а на стройке инструмент выдают под
**материально ответственное лицо (МОЛ)** (ср. карточку МБ-2: кладовщик ведёт учёт, получатель
расписывается за выданное). Итоговый набор:

- [ ] **Администратор / директор** — всё: операции, справочники, пользователи, отчёты. Роли назначает он сам (см. ниже). Обычно смотрит сводку и отчёты, руками операции делает редко.
- [ ] **Кладовщик** — повседневные складские операции (выдача, приём, баланс, ремонт, не найден, списание) и отмена последней операции; справочниками и пользователями не управляет. Это то, что сайт умеет сейчас.
- [ ] **Ответственное лицо** — МОЛ объекта: видит свои объекты (что числится, история) и (позже) ведёт журнал объекта и вложения. **Складские операции пока не делает** — выдаёт и принимает кладовщик; если потом понадобится, разрешим простыми проверками в коде. Кому физически отдали — по-прежнему текст `taken_by`; роль это доступ в систему.
- [ ] **Наблюдатель / гость** — только просмотр баланса и наличия (роль уже есть: `DEMO_USER=гость`). Сюда же рабочие, если дать им просмотр.

Отдельной роли **бригадир не будет** (это `taken_by`).

**Что роль меняет, а что нет.** Роль задаёт: (1) делает операции или только смотрит; (2) доступ к управлению
данными — справочники и пользователи; (3) объём видимости — все объекты или только свои. Правила целостности
журнала роль **не** меняет: журнал только дописывается, отменить можно лишь последнюю операцию по позиции —
это одинаково для всех, кто вообще делает операции (у админа тоже нет «отмены из середины»; правка задним
числом, если когда-то понадобится, — это отдельная корректирующая запись-сторно, не в MVP).

**Термины, чтобы не путать:**
- **Справочники** — master-данные, на которые ссылаются операции: `Category`, `WorkType`, `Site`, карточки `Tool`/`HandTool`. Сейчас правятся в админке; право на правку — у админа (кладовщику частично: заводит позиции и объекты по ходу работы).
- **Журнал объекта** — это **не** справочник, а операционные заметки по дням (планируемая `SiteLogEntry`, см. 2.4). Ведёт ответственное лицо / кладовщик.
- **Отчёты** — сводные выборки («выдано за период», «что на объекте», сводка): их **смотрят и выгружают**, не редактируют. Часть выборок уже есть в `selectors.py`, страниц-отчётов пока нет (на паузе).

**Назначение ролей — через кабинет администратора, не через Django-админку.** Позже делаем директору/админу
простой кабинет управления пользователями и ролями на сайте. До него роли можно раздавать группами Django,
но целевой путь — кабинет.

**Тестовый переключатель ролей (только для стенда).** Чтобы на тесте быстро проверять права, добавить панель
в шапке с кнопками «Админ / Кладовщик / Ответственное лицо / Наблюдатель»: нажал — получил права роли. Правила:
- включается флагом в `.env` (`DEMO_ROLE_SWITCH=1`), по образцу `DEMO_USER`; на боевом переменной нет → панели и логики нет вообще;
- выбранная роль хранится **в сессии**, реального пользователя в базе не меняет (ничего не портится, работает с одним гостем);
- проверки прав — через один помощник (`effective_role(request)` / `can_operate(...)`), а не разбросаны по вьюхам: и переключатель, и боевые группы читают право из одного места; убрать переключатель = убрать флаг и панель, логику прав не трогаем.

**Порядок реализации:**
1. роли-группы + помощник прав + прятать/блокировать кнопки операций тем, кому нельзя;
2. тестовый переключатель ролей (флаг + панель + роль в сессии);
3. привязка объектов к ответственному лицу и расширение модели `Site` (раздел 2.4); позже — кабинет админа.

## 9. Открытые вопросы
- Можно ли принять инструмент, отмеченный ненайденным (нашёлся)? По умолчанию нет.
- Можно ли отменить не последнюю операцию? По умолчанию нет.
- Можно ли передать позицию с одного объекта на другой без возврата? По умолчанию нет.
- Заявка: метка `batch` или отдельная «шапка» (см. DECISIONS.md, решение 7)? пока будет butch.
- К какой выдаче относится частичный приём ручного инструмента, если на объект его выдавали несколько раз? Расчёт будет общим по обьекту, штучный и так будет понятно а количественный просто минусуется от общего количества.
- Формат txt-списка для загрузки (пример строки). С тхт пока подождём, приёмка и выдача по данным из базы галочками избавляет пока от списков.
- Куда и как часто отправлять бэкапы и отчёты; кому оповещения. Бэкапы и списки пока на паузе, просто создаём в моделях поля для их последующей реализации.
