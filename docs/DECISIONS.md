# DECISIONS: принятые решения и причины

Формат: решение, почему так, что отложено.

## 1. Журнал нужен, состояние хранится отдельно
Поля «статус» и «объект» в инструменте показывают только текущее состояние и затираются следующей операцией. Без журнала невозможны отчёты «выдано за период» и «выдано на объект», отмена последнего изменения и разбор ошибочной загрузки. Поэтому: журнал источник истины, статусы и счётчики кэш.

## 2. Статусы как `TextChoices`, не отдельная таблица
Статусов пять, они фиксированные и от них зависит логика («нельзя выдать не найденный»). В базе короткая строка, в интерфейсе русская подпись. Новый статус это правка кода и миграция.

## 3. Два вида учёта, два плоских журнала
Штучный (`Tool`) и количественный (`HandTool`) имеют каждый свой журнал (`ToolMovement`, `HandToolMovement`) с общим абстрактным родителем `BaseMovement`. Причина: нет ветвлений в `services.py` и в запросах, у каждого вида своя простая функция. Цена: общие отчёты по обоим видам склеиваются в `selectors.py` из двух запросов.
Отвергнуто: один журнал с двумя необязательными ссылками (нужны проверки «заполнена ровно одна»), один журнал с наследованием не абстрактного родителя (Django создаст вторую таблицу и запретит переопределять поле).

## 4. Правило учёта по стоимости
Дорогое и значимое заводится как штучное (`Tool`), дешёвое и массовое как `HandTool`. Решать нужно при постановке на баланс: перевод между видами позже неудобен (списать из одной модели, завести в другой). Сомневаешься, заводи штучным.

## 5. Постановка на баланс это событие журнала
Тип `added`: для штучного +1, для ручного +N к `total` с комментарием в `note`. Закупки за период берутся из журнала одинаково для обоих видов. Дата «поставлен на баланс» в `Tool` остаётся справочно.

## 6. Изменения состояния только через `services.py`
- Статусы и счётчики закрыты от правки в админке (только чтение).
- Запись в журнал и изменение статуса или счётчика в одной транзакции (`transaction.atomic`, `select_for_update`).
- Ограничение `issued <= total` в базе.
- Отмена: запись помечается `is_cancelled`, состояние пересчитывается из журнала, а не откатывается обратной арифметикой.
- Формы выдачи и приёма (галочки) берут данные из базы в реальном времени; проверки в форме для удобства, настоящая проверка в сервисе (данные могут прийти из API или бота).

## 7. Заявка: метка `batch` сейчас, «шапка» позже при необходимости
- **Сейчас:** в журналах необязательное поле `batch` (UUID). Одна выдача набора из N позиций это N строк с одним `batch`. Фильтр по `batch` показывает набор, отмена набора это отмена всех его строк. Ничего дополнительного не хранится.
- **Шапка (модель `Issue`):** отдельная запись «документ выдачи» (объект, кто взял, время, автор, комментарий, признак отмены), к которой строки привязаны внешним ключом. Нужна, если понадобятся номер заявки, плановая дата возврата, комментарий ко всей заявке, явный статус «открыта / частично закрыта / закрыта», быстрый список заявок без группировки строк.
- **Переход потом:** по каждому уникальному `batch` создаётся `Issue`, поле заменяется внешним ключом. Данные не теряются.
- Не заводить в этот раз три класса выдачи (шапка + две таблицы строк): избыточно для текущих задач.

## 8. Объект один на штучную позицию, для ручной считается
В `Tool` кэш `current_site`. Для `HandTool` одного объекта быть не может (5 молотков на одном, 3 на другом), поэтому «что на каком объекте» считается запросом по журналу (выдано минус принято минус не найдено минус списано, без отменённых).

## 9. Сотрудники и бригады отложены
Вместо них в журнале текстовое поле `taken_by`. Позже заменяется ссылкой на модель сотрудников или бригад. Серийный номер, гарантия и документы у инструмента убраны как лишние на этом этапе.

## 10. Фото
Отдельная модель `ToolPhoto` (много фото на инструмент, одно главное, ограничение в БД «не больше одного главного»). Нужны Pillow, `MEDIA_URL`, `MEDIA_ROOT`. Папка `media/` в `.gitignore`.

## 11. Интерфейсы
- Бэкенд на DRF, вьюхи тонкие, логика в `services.py` и `selectors.py`. Так сайт, бот используют одни функции.
- Сначала адаптивный сайт (возможно PWA). Telegram-бот только для оповещений директору и сводок (достаточно токена бота и chat id; получатель должен один раз нажать Start).

## 12. База и окружение
- Перейти на PostgreSQL до написания `services.py` с блокировками: на SQLite `select_for_update` ничего не делает.
- Python 3.12, `.env` для секретов, `.env.example` в репозитории.
- `SECRET_KEY` из `startproject` пока допустим (insecure, только dev), до деплоя вынести в `.env`, на сервере использовать другой ключ.
- `LANGUAGE_CODE = 'ru'`, `TIME_ZONE = 'Europe/Moscow'`.

## 13. Правила по умолчанию (самые строгие, менять по решению владельца)
- Нельзя принять позицию, числящуюся не найденной.
- Нельзя отменить не последнюю операцию по позиции.
- Нельзя выдать позицию, уже числящуюся выданной (передача между объектами через приём и новую выдачу).

## 14. Не найден, списание, ремонт, ручной инструмент
- **Не найден (`missing`):** позиция вычитается из «числится на объекте», запись в журнале остаётся (история сохраняется).
- **Списание (`written_off`):** вычитается и из склада, и с объекта.
- **Ремонт (`servicing`):** возврат из ремонта это `returned` без объекта.
- **Ручной инструмент (`HandTool`):** статусов и `servicing` нет, только количество (`total`, `issued`).
- Приём ручного инструмента считается общим по объекту, а не по конкретной выдаче: количество просто вычитается из числящегося на объекте. Поэтому `batch` нужен только для группировки строк и отмены набора, а не для привязки приёма к выдаче.
- Каждая новая операция получает новый `batch`; он не наследуется от предыдущих операций на том же объекте.
- **Ручной инструмент: `total` это то, чем реально можно снабдить людей.** `missing` и `written_off` уменьшают `total`; сами записи остаются в журнале, отчёты по потерям и списаниям строятся фильтром по журналу. Если позиция списана или потеряна на объекте, она уменьшает и `issued` (она числилась на объекте). Формулы пересчёта: `total = added − missing − written_off`; `issued = issued − returned − missing − written_off (только записи с объектом)`; `available = total − issued`.
- **Операции из раздела 14 и откуда их можно делать (штучные):** `missing` только с объекта (статус «выдан» на этом объекте); `servicing` и `written_off` либо со склада (`site` не указан), либо с объекта (`site` указан, позиция выдана на нём). Со склада списывается позиция со статусом «на складе» или «в ремонте»; «не найденную» тоже можно списать (потеря и списание различаются названием для наглядности, потерянное закрывается списанием). Потерянный ручной инструмент списывать не нужно: он уже вычтен из `total` при отметке «не найден». Выдать или принять потерянную позицию нельзя. Выборки «числится на объекте» для штучных должны брать последнее действующее состояние позиции, чтобы «не найден», затем «списан» не считались дважды.

## 15. Отмена операций
- Отмена это флаг `is_cancelled` на строке журнала; строки не удаляются и не правятся. После этого состояние позиции пересчитывается по оставшимся действующим записям (`recalc_*`), а не откатывается обратной арифметикой.
- `cancel_batch` отменяет набор целиком, `cancel_movement` одну запись (например, одну позицию, ошибочно попавшую в набор).
- Отменить можно только последнюю действующую операцию по позиции (правило 13). Для ручного инструмента правило то же и действует по всей позиции, а не по объекту: если по молоткам после выдачи были другие операции на любом объекте, сначала отменяются они, по порядку. Цена строгости: при частых операциях отменять приходится «с конца». Смягчить можно позже, если это будет мешать.
- Набор отменяется всё или ничего; ошибка перечисляет все проблемные позиции.
- Постановку на баланс (`added`) отменять нельзя: ошибки прихода исправляются отдельной операцией (инвентаризация, позже).
- Кто и когда отменил хранится в `cancelled_by` и `cancelled_at` (`BaseMovement`); заполняет только `services.py`.

## 16. Смена категории не пишется в журнал
- Категория это справочный признак позиции, а не движение: она не меняет ни остаток, ни статус, ни место. Поэтому перенос позиции в другую категорию или подкатегорию в журнал не пишется (журнал только про движение: приход, выдача, приём, потери, списание, ремонт, отмена).
- Отчёты по категориям пока строятся по текущей категории позиции через модели `Tool` и `HandTool` (фильтр и группировка по `category`). Группировку по категориям и подкатегориям добавим позже, когда понадобятся такие отчёты.
- Следствие: если позицию перенесли, старые операции в отчётах «переедут» вместе с ней в новую категорию. Если потребуется история категорий, добавим отдельный журнал изменений справочных полей (кто, когда, было, стало), а не строки в журналах движения.

## 17. Сайт: шаблоны Django, темы на переменных
- Фронтенд это страницы Django (`apps/web`) с минимумом JavaScript; для форм выдачи и приёма позже HTMX. Отдельный React или Vue не нужен, а API остаётся для бота и других клиентов.
- Внешний вид задаётся переменными в `app.css`: две темы, `summit` (горы, стекло) и `nexora` (плоские карточки, ядовитый зелёный). Переключатель в верхней панели, выбор запоминается в браузере. Смена цветов или новая тема правится в переменных, а не в шаблонах.
- Картинка героя главной это переменная `--hero-art`: сейчас свой векторный рисунок гор (`mountains.svg`), фотографию можно подставить одной строкой.
- Логотип: `logo-alp-dark.png` (светлый вариант для тёмного фона, сделан из исходного), оригинал сохранён как `logo-alp-light.png`.
- «Парк в строю» (`ready_percent`) = (на складе + выдано) / (на складе + выдано + в ремонте + не найдено); списанное не считается, если считать нечего, то 100%. Выдача инструмента на объект готовность не снижает.
- Анимации отключаются, если в системе включено «уменьшить движение»; на узких экранах размытие карточек слабее, чтобы не тормозили телефоны.

## 18. Движение на сайте не зависит от флага системы

Флаг `prefers-reduced-motion` у владельца включён (в Windows выключены анимации), и сайт «умирал»: переходы
по 0.01 мс, не работал плавный скролл. Для внутреннего инструмента решили не учитывать этот флаг.
Режим «меньше движения» включается явно: `localStorage.setItem("motion", "reduced")` (атрибут `data-motion`
на `<html>`, его ставит скрипт в base.html). Если сайт пойдёт к внешним пользователям, вернуть учёт флага системы.

## 19. Формы выдачи и приёма на сайте

Страницы `/operations/issue/` и `/operations/receive/` (apps/web), логика только через services (`issue_to_site`,
`receive_from_site`), вьюхи тонкие. Форма присылает `tools=<id>` (флажки штучного) и `qty_<id>` (количество
ручного, пусто или 0 значит «не выбрано»); разбор формата в `apps/web/positions.py`, правила учёта проверяет
service. При отказе (ServiceError) ничего не записано, страница показывает все строки ошибок, выбор сохраняется.
Успех: сообщение (тост) и redirect на ту же страницу (чтобы F5 не повторил операцию).
Приём: список позиций зависит от объекта. При выборе объекта HTMX запрашивает ту же страницу с `?site=<id>`
и заменяет только блок `#positions` (сервер отдаёт кусок по заголовку HX-Request). Без HTMX (CDN недоступен)
скрипт перезагружает страницу с `?site=`. Выбор объекта в приёме не ограничен объектами с остатком:
у пустого объекта покажем «ничего не числится».

## 20. «Не найден», списание, ремонт на сайте

Страницы `/operations/missing/`, `/write-off/`, `/servicing/`, `/from-servicing/`: тот же шаблон и блок позиций, что у выдачи
и приёма (в «Операциях» шесть вкладок). Общий ход в `_site_operation` (apps/web/views.py), все изменения только через
services. Что показывается для выбора, решает `_lists(mode, site)`:
- «Не найден»: объект обязателен, показываем то, что числится на нём (штучные и ручной с количеством).
- Списание: поле «Откуда», пустое значение значит склад. Со склада показываем штучные «на складе», «в ремонте» и «не найден»
  (с подписью статуса) и ручной в наличии; с объекта то, что числится на нём.
- Ремонт: только штучные. Со склада «на складе», с объекта числящиеся на нём. Если форма всё же пришлёт ручной, отказ.
- Из ремонта: объекта нет, показываем штучные со статусом «в ремонте».
В полях «Откуда» пустой вариант «Склад» настоящий выбор, а не подсказка, поэтому у select стоит `data-dd-keep`
(свой выпадающий список не рисует его серым как подсказку).


## 21. Герой главной: фото-фон и логотип с бликами
- Фон — одно фото горы (`static/web/img/hero/matterhorn.webp`), без нарезки на слои: нарезка давала кривые края. Параллакс слабый (сдвиг до ~3 px) и тяжёлый на сглаживание, чтобы не дёргалось.
- Логотип (`logo-alp-3d.png`) рисуется WebGL-шейдером: рельеф берётся из яркости текстуры, золото (насыщенные тёплые пиксели) даёт широкий тёплый блик, карбон — мелкие искры по зерну. Нет WebGL — обычная `<img>`.
- Три слоя глубины: фото (0.5), текст и кнопка в `.hero-mid` (0.9), большой логотип поверх горы (2.2). Параллакс в `hero.js`, блики во всех логотипах в `logo3d.js` (подключён в base.html: меню и вход тоже на шейдере).
- Свет: пока курсор над логотипом, блик идёт за ним; иначе раз в ~6,5 с (малые логотипы раз в 13 с, `data-sweep`) сам пробегает слева направо.
- Вне экрана цикл анимации останавливается. При `data-motion="reduced"` (§18) всё стоит на месте.
- Для меню и входа используется обычный `logo-alp.png`.

## 22. Эффекты под курсором и на иконках
- Фото героя дублируется в WebGL-холст (`scene-fx.js`): настоящая рябь (волновое уравнение на сетке 128×192 на CPU, в GPU уходит текстура наклона и высоты воды) и RGB-расслоение. Курсор роняет капли вдоль пути; чем быстрее мышь, тем крупнее и сильнее волны и RGB; левая кнопка зажата и тянем — максимум. Искажается только эта картинка: WebGL не может «продавить» обычный HTML под собой. Мышь замерла — цикл перерисовки останавливается. Нет WebGL или `data-motion="reduced"` — остаётся обычная `<img>`.
- Иконки (`.icon-tile`): блик на CSS (`tile-sheen`), без WebGL. Лимит браузера ~16 контекстов делает «шейдер на каждую иконку» непригодным; если понадобятся стеклянные иконки, делать один общий холст на страницу.

## 23. Экономный режим анимаций
- Логотипы (`logo3d.js`) перерисовываются только пока бежит блик или курсор рядом; между бликами остаётся готовый кадр, таймер будит цикл к началу следующего блика. В тихом окне ноль вызовов requestAnimationFrame.
- Параллакс (`hero.js`) без курсора возвращается в центр и засыпает; постоянного «дыхания» больше нет.
- Рябь (`scene-fx.js`): работает и от пальца (касание роняет каплю, горизонтальное движение даёт волны; вертикаль отдана прокрутке через `touch-action: pan-y`). Рисуется только во время касания и ~2 с после, поэтому батарею почти не тратит. На телефонах и слабых устройствах (≤4 ядер, ≤4 ГБ, `prefers-reduced-data`) холст вдвое меньше. Над большим логотипом волны не создаются.
- Телефон: логотип в потоке над текстом, а не поверх него.

## 24. Отмена и история в интерфейсе
- Страница «Журнал» (`/journal/`): операции по обоим журналам, наборы (общий batch) сгруппированы в одну карточку. У набора кнопка «Отменить набор», у каждой строки «Отменить» (`services.cancel_batch` / `cancel_movement`, правила из раздела 13 не менялись).
- «Можно ли отменить» считает селектор (`journal_entries`, `_movement_dicts`) теми же правилами, что `services._cancel`, только чтобы показать кнопку или причину в подсказке. Окончательный запрет всегда за сервисом: нажатие на устаревшей странице закончится понятным сообщением.
- Набор можно отменить, только если можно отменить каждую его действующую строку (всё или ничего); иначе кнопка неактивна, в подсказке первая причина.
- Страницы позиций: `/inventory/tool/<id>/` и `/inventory/hand/<id>/` с историей операций (отменённые видны, приглушены) и кнопками отмены.
- Отмена только POST + CSRF; после неё возврат на страницу, откуда нажали (`next`, только свой сайт), результат в плашке. Кнопка двухшаговая: первое нажатие «Точно отменить?», второе в течение 4 секунд отправляет форму (без JS форма уходит сразу).
- Права пока общие: отменять может любой вошедший. Разделение ролей в плане «права».
- Набор в журнале это одна строка-«гармошка» (`<details>`, без JS): «Выдан · Объект · N поз.», в подписи первые позиции; раскрывается в список позиций, у каждой своя отмена. Кнопка «Отменить набор» стоит в строке и привязана к форме через атрибут `form`, поэтому нажатие по ней не раскрывает набор. Одиночные операции остаются обычными строками.
- В инвентаре адрес (`current_site`) показан сразу после статуса, а не в подписи под названием.
- `seed_demo`: 25 электро и 25 ручных позиций, плюс категория «Высотное снаряжение» (20 штучных с номерами и 10 количественных), 5 объектов; существующее по названию пропускается, ничего не дублируется и не меняется. (На время сокращали до 20 и 10, вернули: для наглядности позиции добавляются руками.)

## 25. Инвентарь сгруппирован по категориям
- Страница инвентаря: крупный заголовок категории в акцентном цвете, под ним все её позиции, сначала штучные, потом количественные (`selectors.group_by_category`). Категории по алфавиту, подкатегория подписывается «Родитель / Подкатегория». Одна категория может содержать оба вида учёта (раздел 16: категория только справочный признак).
- Поиск и фильтр статуса работают как раньше, пустые категории не показываются. Разметка позиций вынесена в `_item_tool.html` и `_item_hand.html`.

## 26. Деплой: Docker Compose и Caddy
- Три контейнера: PostgreSQL, Django под gunicorn, Caddy. Caddy сам выпускает HTTPS-сертификат и раздаёт статику и фото из общих томов, поэтому лишних пакетов (whitenoise) в проекте нет.
- Настройки сервера только через `.env` (DEBUG, SECRET_KEY, DOMAIN, HTTPS, при необходимости ALLOWED_HOSTS и CSRF_TRUSTED_ORIGINS). Без `.env` на своём компьютере всё работает как раньше: DEBUG по умолчанию включён. При `DEBUG=0` без `SECRET_KEY` Django не запускается.
- Бэкап базы: `scripts/backup.sh` (дамп через контейнер db, хранение 14 дней). Инструкция: `docs/DEPLOY.md`.
- Тестовый и боевой стенды разделены, потому что журналы только дописываются.

## 27. Категории-аккордеоны и сгруппированные операции на главной
- Инвентарь: заголовок категории (тот же крупный вид) это `<summary>` нативного `<details>`, без JS-библиотек. Без поиска и фильтра категории свёрнуты, а какие открыты, запоминается в браузере (localStorage, `app.js`); при поиске или фильтре статуса всё раскрыто сервером и состояние не сохраняется.
- Главная: «Последние операции» берутся из тех же записей, что и журнал (`selectors.recent_entries` поверх `journal_entries`). Набор из нескольких позиций это одна строка «Тип · Объект · N поз.», ссылка на `/journal/?batch=<uuid>` (журнал с одним раскрытым набором). Одиночная операция показывается как раньше.
- `selectors.recent_movements` удалена: её заменила `recent_entries`.


## 28. Постановка на баланс на сайте
- Вкладка «На баланс» в операциях (`/operations/add/`). Штучное: название, категория и сколько одинаковых штук завести (1–50): `services.register_tools`, все записи `added` с одним batch, в журнале это один набор. Количественное: пополнить существующую позицию (`add_hand_tool_stock`) или завести новую (`register_hand_tool`, total = 0 и сразу +N).
- Постановка на баланс по-прежнему не отменяется (см. раздел про отмену): ошибку исправляют списанием.

## 29. Фото на сайте
- Фото не часть учёта: не меняет статус и не пишет в журнал. Загрузка при постановке на баланс (одно фото на все заведённые штуки, файл сохраняется один раз) и на странице позиции (несколько файлов, «Сделать главным», «Удалить»). Первое фото позиции становится главным само; главное всегда одно (ограничение в БД), при удалении главного главным становится самое раннее из оставшихся.
- Фото только у штучных (`Tool`); у количественных (`HandTool`) модели фото нет.

## 30. Показ через Cloudflare Tunnel
- Для показа без сервера: `runserver` на своём компьютере и `cloudflared tunnel --url`. Наружу только с `DEBUG=0` и своим `SECRET_KEY`: при `DEBUG=1` посетители видели бы трейсбеки с настройками.
- При `DEBUG=0` статику и фото отдаёт Caddy, а у туннеля его нет. Флаг `SERVE_FILES=1` включает раздачу через Django (`config/urls.py`). Медленнее Caddy, для показа достаточно; whitenoise по-прежнему не нужен (раздел 26).
- `SECURE_PROXY_SSL_HEADER` годится и для туннеля: cloudflared передаёт `X-Forwarded-Proto: https`.
- Ошибки 500 пишутся в консоль при любом `DEBUG` (LOGGING в settings).
- Показ на отдельной базе: прав пока нет, а журнал только дописывается (как с тестовым стендом, раздел 26).
