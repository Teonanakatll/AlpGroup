# AlpGroup: контекст проекта для Claude

Складской учёт инструмента и снаряжения, выдача на объекты.
Требования: docs/SPEC.md. Принятые решения и причины: docs/DECISIONS.md.
Владелец проекта давно не писал код (хочет вспомнить Django и DRF): объясняй решения коротко, код давай читаемый, сложные места поясняй.

## Стек
Python 3.12, Django, Django REST Framework. PostgreSQL (настройки в .env). Сайт: шаблоны Django (apps/web) и HTMX для форм (подключён с CDN); Telegram-бот только для оповещений.

## Структура
- config/ — настройки и urls
- apps/inventory/ — Category, Tool, ToolPhoto, HandTool, BaseMovement (abstract), ToolMovement, HandToolMovement
- apps/sites/ — Site, WorkType (минимальный справочник)
- apps/staff/ — роли: группы Django и единый помощник прав `roles.py` (effective_role, can_operate, can_manage, operator_required, контекст-процессор), `permissions.py` (CanOperate для DRF)
- apps/web/ — сайт: страницы, шаблоны, стили (app.css, 10 тем на переменных: палитра data-theme + режим data-mode dark/light, список в themes.py), иконки, логотип; формы операций: выдача, приём, не найден, списание, ремонт (views.py, forms.py, positions.py); журнал с отменой и история позиции
- в каждом приложении services.py (изменения), selectors.py (выборки), tests/

## Ключевые правила (подробности в DECISIONS.md)
- Журналы только дописываются. Источник истины журнал; статус и счётчики в моделях кэш.
- Состояние меняется только в services.py, в одной транзакции с записью в журнал (atomic + select_for_update). Поля статусов и счётчиков в админке только для чтения.
- Отмена: is_cancelled, затем пересчёт состояния из журнала.
- Два вида учёта: Tool (штучно, дорогое), HandTool (количеством, дешёвое).
- Выдача набора: общий UUID batch у строк журнала.
- Вьюхи DRF тонкие, логика только в services.py и selectors.py.
- Статусы и типы операций через TextChoices.
- Секреты через .env, в репозитории .env.example. Не коммитить .venv, .env, db.sqlite3, media/, .idea/, __pycache__/.
- Тесты на services и selectors (pytest-django). Коммиты: одна мысль, префикс feat/fix/refactor/docs/test/chore.

## Как запускать
1. Создать venv и активировать его, затем `pip install -r requirements.txt`.
2. Создать `.env` по образцу `.env.example` (параметры PostgreSQL).
3. `python manage.py migrate`, `python manage.py createsuperuser`.
4. `python manage.py runserver`, сайт на http://127.0.0.1:8000/ (вход тем же логином, что в админке), админка на /admin/, API на /api/.
5. Тесты: `pytest`.
6. Деплой на сервер (Docker, Caddy, бэкапы): docs/DEPLOY.md; пошагово с нуля на Hetzner с Windows: docs/SERVER.md (тестовый стенд: Hetzner CX23, Helsinki). Показ тестового стенда без входа: DEMO_USER=гость в .env, переключатель ролей: DEMO_ROLE_SWITCH=1 (docs/DEPLOY.md, раздел 7).
7. Тестовые данные (45 штучных и 35 ручных позиций, из них снаряжение: 20 штучных и 10 количественных): `python manage.py seed_demo` (повторный запуск ничего не дублирует).

## Окружение и как работаем
- Владелец: Windows, командная строка cmd; живёт в Батуми (Грузия). Отвечать по-русски.
- Ветки: Claude делает `claude/<тема>` от свежего main и пушит; владелец сам мержит, гоняет `pytest` у себя и пушит main. Шпаргалка владельца: docs/tips.md.
- У Claude в облачной сессии PyPI закрыт: зависимости не ставятся, pytest и сайт не запускаются. Тесты проверяет владелец; в ответе честно писать, что не запускалось.
- Тестовый стенд: https://alpgroup.ezolab.dev (Hetzner CX23, Helsinki, IP 135.181.195.12, Ubuntu 24.04, Docker Compose из репозитория, `.env` только на сервере). Домен ezolab.dev куплен в Cloudflare, A-запись в режиме DNS only, сертификат выпускает Caddy. База стенда тестовая (seed_demo).
- Обновить стенд после мержа (на сервере): `cd ~/alpgroup && git pull && docker compose up -d --build`.
- Боевого сервера пока нет; когда будет, отдельным сервером с чистой базой (DEPLOY.md, раздел 5).
